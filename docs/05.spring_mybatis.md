# 1. MyBatis

## 1.1 MyBatis 개요와 SQL 매퍼 패러다임

### 1.1.1 SQL 중심 데이터 접근 기술의 발전 흐름과 패러다임
- 순수 JDBC: 자바 소스코드 내에 SQL 문자열이 직접 하드코딩되고 Connection, PreparedStatement, ResultSet 등 반복적인 자원 획득과 해제 보일러플레이트 코드가 과도하게 발생함.
- 스프링 JdbcTemplate: 반복적인 자원 관리와 예외 변환을 프레임워크가 자동화했으나, 여전히 복잡하고 긴 SQL 문이 자바 클래스 내부에 문자열 형태로 혼재되어 가독성과 유지보수성이 저하됨.
- MyBatis: 복잡한 SQL 문을 자바 코드로부터 격리하여 독립된 XML 파일(또는 어노테이션)로 분리 관리하고, 실행 결과를 자바 객체(Record, DTO)에 자동으로 바인딩해 주는 대표적인 SQL 매퍼(SQL Mapper) 프레임워크.

[데이터 접근 기술 3대 패러다임 비교]

| 구분 | JdbcTemplate | MyBatis | JPA / Spring Data |
| :--- | :--- | :--- | :--- |
| 패러다임 | SQL 중심 직접 실행 | SQL 매퍼 (SQL Mapper) | 객체-관계 매핑 (ORM) |
| SQL 작성 위치 | 자바 소스코드 내부 문자열 | 독립된 XML 파일 또는 어노테이션 | 프레임워크가 자동 생성 |
| 동적 쿼리 제어 | 복잡한 문자열 결합(StringBuilder) | 풍부한 동적 XML 태그(`<if>`, `<choose>` 등) | Criteria API / Querydsl 컴파일 타임 검증 |
| 객체 매핑 방식 | RowMapper 수동 구현 필요 | XML resultMap 및 컬럼명 자동 매핑 | 엔티티 어노테이션 기반 자동 객체 매핑 |
| 주요 적합 분야 | 단순 관리자 도구, 배치 스크립트 [^1] | 복잡한 통계 쿼리, 기존 레거시 SQL 유지보수 | 도메인 주도 설계 [^2] (DDD), 비즈니스 로직 중심 |

### 1.1.2 MyBatis의 핵심 역할과 자동화 메커니즘
- SQL과 자바 코드의 완전한 분리
  - 복잡한 SQL 쿼리문을 자바 소스코드에 하드코딩하지 않고 독립된 XML 파일로 격리하여 관리함.
  - 쿼리 수정 시 자바 코드를 다시 컴파일하지 않고 XML 파일 수정만으로 대응할 수 있어 유지보수성이 향상됨.
- 인터페이스 선언 기반의 자동 실행
  - 개발자가 데이터베이스 연동을 위한 DAO 구현 클래스를 직접 만들지 않고, `@Mapper` 인터페이스에 메서드 시그니처만 선언함.
  - MyBatis가 인터페이스 메서드 호출을 감지하여 매퍼 XML에 정의된 동일한 ID의 SQL 쿼리를 자동으로 찾아 실행함.
- 파라미터 바인딩과 결과 객체(DTO) 자동 매핑
  - 자바 메서드로 전달한 DTO나 단일 파라미터를 SQL의 `#{}` 위치에 PreparedStatement 파라미터로 자동 바인딩함.
  - 데이터베이스에서 조회된 ResultSet 결과 데이터를 선언한 반환 타입(Record/DTO) 객체의 필드에 카멜 케이스 규칙에 맞추어 자동으로 조립하여 반환함.

## 1.2 MyBatis 핵심 구성 요소와 동작 원리

### 1.2.1 MyBatis 개발 시 작성하는 핵심 파일의 종류와 역할
- MyBatis 기반 데이터 접근 계층을 구현할 때 일반적으로 3가지 핵심 파일(DTO, Mapper 인터페이스, Mapper XML)을 세트로 구성함.

#### 1) 데이터 전송 객체 (Record / DTO)
- DTO (Data Transfer Object)
  - 계층 간(데이터베이스 ↔ 데이터 접근 계층 ↔ 서비스 계층 ↔ 컨트롤러) 데이터 교환을 전담하는 순수 자바 객체.
  - 별도의 비즈니스 로직을 포함하지 않고 오직 전달할 데이터(필드)만을 캡슐화하여 전달하는 데이터 바구니 역할을 수행함.
- Record (Java 16+ 표준 불변 데이터 모델)
  - 불변(Immutable) 데이터를 간결하게 표현하기 위해 도입된 자바의 특수 클래스 선언 문법(class 선언 대신 record로 선언).
  - 선언만으로 모든 필드가 `private final`로 지정되며, 전체 매개변수 생성자, 필드명과 동일한 이름의 Getter 메서드, `equals()`, `hashCode()`, `toString()`이 컴파일러에 의해 자동 생성됨.
- 일반 클래스(POJO) DTO와 Record 선택 기준
  - Record 선택이 적합한 경우
    - 단순 단건 및 목록 조회 응답 DTO: 데이터베이스 조회 결과를 정규 생성자로 한 번에 바인딩하므로 불변성과 스레드 안전성을 확보하고 보일러플레이트 코드를 최소화함.
    - 검색 조건 파라미터 DTO: 여러 검색 조건을 읽기 전용으로 전달할 때 데이터 임의 변조를 사전에 방지함.
    - 1:1 조인 하위 객체 또는 1:N 컬렉션의 개별 원소 객체: `<constructor>` 태그를 통해 생성자 인자로 한 번에 주입받을 수 있음.
  - 일반 클래스(POJO/Lombok) 선택이 적합한 경우
    - 자동 생성 기본키(PK)를 주입받는 등록 DTO: MyBatis의 `useGeneratedKeys` 및 `keyProperty` 기능이 사후에 생성된 PK 값을 Setter(`setId()`)로 주입해야 하므로 가변 필드가 필요함.
    - 1:N 조인 쿼리의 최상위 결과 DTO: 여러 행(Row)으로 반환되는 조인 결과를 순회하며 컬렉션(`List`)에 하위 객체들을 점진적으로 누적 추가(`add`)해야 하므로 기본 생성자와 접근자가 열려 있는 클래스 구조가 필요함.
  
- 게시글 생성 요청 DTO (src/main/java/net/likelion/bebc25/sns/dto/PostCreateDto.java)
  ```java
  package net.likelion.bebc25.sns.dto;

  import lombok.AllArgsConstructor;
  import lombok.Builder;
  import lombok.Getter;
  import lombok.NoArgsConstructor;
  import lombok.Setter;

  @Getter
  @Setter
  @NoArgsConstructor
  @AllArgsConstructor
  @Builder
  public class PostCreateDto {
      private Long id;
      private Long memberId;
      private String content;
      private String imageUrl;

      public PostCreateDto(Long memberId, String content, String imageUrl) {
          this.memberId = memberId;
          this.content = content;
          this.imageUrl = imageUrl;
      }
  }
  ```

- 게시글 조회 응답 DTO (src/main/java/net/likelion/bebc25/sns/dto/PostResponseDto.java)
  ```java
  package net.likelion.bebc25.sns.dto;

  import java.time.LocalDateTime;

  public record PostResponseDto(
      Long id,
      Long memberId,
      String content,
      String imageUrl,
      LocalDateTime createdAt,
      LocalDateTime updatedAt
  ) {}
  ```

#### 2) 매퍼 인터페이스 (Mapper Interface)
- `@Mapper` 어노테이션을 부여하고 SQL 실행 메서드의 시그니처만 선언하는 자바 인터페이스.
- 별도의 DAO 구현 클래스를 작성하지 않고 인터페이스 선언만으로 데이터베이스 연동이 가능함.

- PostMapper 인터페이스 (src/main/java/net/likelion/bebc25/sns/mapper/PostMapper.java)
  ```java
  package net.likelion.bebc25.sns.mapper;

  import net.likelion.bebc25.sns.dto.PostResponseDto;
  import org.apache.ibatis.annotations.Mapper;
  import org.apache.ibatis.annotations.Param;

  @Mapper
  public interface PostMapper {

      // ID 기반 게시글 단건 조회
      PostResponseDto findById(@Param("id") Long id);
  }
  ```

#### 3) 매퍼 XML 파일 (Mapper XML)
- 실제 데이터베이스에서 실행할 SQL 쿼리문(`<select>`, `<insert>` 등)과 조회 결과(ResultSet)와 객체(DTO)를 매핑하는 규칙(단일 매핑 및 ResultMap 복합 조인 매핑)을 작성하는 XML 파일.
- 상단의 `<mapper namespace="...">` 속성에 매퍼 인터페이스의 전체 패키지 경로를 지정하고, 태그의 `id` 속성을 인터페이스 메서드명과 일치시켜서 작성.

- PostMapper.xml 파일 (src/main/resources/mapper/PostMapper.xml)
  ```xml
  <?xml version="1.0" encoding="UTF-8" ?>
  <!DOCTYPE mapper
          PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
          "https://mybatis.org/dtd/mybatis-3-mapper.dtd">

  <mapper namespace="net.likelion.bebc25.sns.mapper.PostMapper">

      <select id="findById" parameterType="long" resultType="PostResponseDto">
          SELECT id, member_id, content, image_url, created_at, updated_at
          FROM post
          WHERE id = #{id}
      </select>

  </mapper>
  ```

#### 4) 개발 흐름 및 파일 간의 유기적 상호작용
- 1단계 (DTO 정의): 데이터베이스 테이블 컬럼 구조에 맞추어 요청/응답용 Record DTO를 정의함.
- 2단계 (Mapper 인터페이스 선언): 서비스 계층에서 호출할 메서드명과 반환 타입을 `@Mapper` 인터페이스에 선언함.
- 3단계 (Mapper XML 작성): XML 상단의 `<mapper namespace="...">`에 매퍼 인터페이스의 전체 패키지 경로를 지정하고, 인터페이스 메서드명과 동일한 `id` 값을 가진 태그(`<select id="...">`)를 작성하여 SQL을 매핑함.

### 1.2.2 Mapper 인터페이스의 내부 동작 원리와 동적 프록시
- MyBatis 3대 핵심 컴포넌트
  - SqlSessionFactory: 설정 정보와 매퍼 XML을 파싱하여 애플리케이션 시작 시점에 생성되는 싱글톤 팩토리 객체.
  - SqlSession: SQL 실행 및 트랜잭션 제어를 담당하는 핵심 인터페이스.
  - SqlSessionTemplate: 스프링 부트 환경에서 스프링 트랜잭션 매니저와 연동되어 멀티스레드 환경에서도 안전하게 싱글톤으로 공유되는 SqlSession 구현체.

#### 1) 스프링 부트 기동 시점: 자동 구성에 의한 빈 조립 과정
- 스프링 부트 애플리케이션이 시작될 때 `mybatis-spring-boot-starter`의 자동 구성(Auto-Configuration) 모듈이 동작하여 핵심 객체들을 순차적으로 생성하고 스프링 컨테이너에 등록함.

```
[application.yaml 설정] + [DataSource 커넥션 풀]
                        │
                        ▼ (1) 설정과 커넥션 풀을 기반으로 싱글톤 생성
               [SqlSessionFactory]
                        │
                        ▼ (2) 트랜잭션 연동 및 멀티스레드 안전성 보장을 위해 래핑
              [SqlSessionTemplate]
                        │
                        ▼ (3) @Mapper 인터페이스를 스캔하여 프록시 생성 및 주입
        [@Mapper 동적 프록시 Bean (PostMapper)]
```

- @Mapper 인터페이스 스캔과 동적 프록시 [^3] 생성
  - 개발자가 별도의 DAO 구현 클래스를 작성하지 않아도, 프레임워크가 인터페이스를 기반으로 런타임에 동적 프록시 객체를 자동 생성함.
  - 생성된 동적 프록시 객체 내부에 `SqlSessionTemplate`을 탑재하여 서비스 계층에 스프링 빈으로 주입함.

#### 2) 런타임 실행 시점: 쿼리 실행 및 결과 반환 위임 흐름
- 서비스 계층에서 매퍼 인터페이스의 메서드를 호출했을 때 실제 내부에서 처리되는 단계별 위임 메커니즘.

```
[1. Service 계층] ──> postMapper.findById(1L) 호출
                             │
                             ▼ (호출 가로챔)
[2. 동적 프록시 Bean] ──> MapperProxy가 메서드명과 매퍼 XML의 SQL 태그 ID를 연결
                             │
                             ▼ (실행 위임)
[3. SqlSessionTemplate] ──> 스프링 트랜잭션 동기화 저장소에서 현재 DB 커넥션 획득
                             │
                             ▼ (쿼리 실행)
[4. 매퍼 XML SQL]   ──> PreparedStatement 바인딩 후 SELECT 쿼리 수행
                             │
                             ▼ (결과 변환)
[5. DB ResultSet]   ──> PostResponseDto 객체 필드로 자동 매핑 후 Service에 최종 반환
```

## 1.4 Mapper 인터페이스와 매개변수 바인딩

### 1.4.1 @Param 어노테이션 활용 기준
- 단일 DTO / Record 객체를 전달할 때
  - `@Param`을 생략하고 넘기는 것이 표준 관례이며, XML에서는 DTO 내부 필드명을 `#{content}`, `#{imageUrl}` 형태로 직접 꺼내어 사용함.
  - 만약 단일 DTO 앞에 `@Param("post")`를 부여하면 XML에서도 반드시 `#{post.content}`, `#{post.imageUrl}`처럼 지정한 별칭을 접두어로 붙여서 접근해야 함.
  - DTO와 단일 값(예: `memberId`)을 동시에 넘길 때는 이름 충돌을 방지하기 위해 DTO 앞에도 `@Param("post")`를 선언하며, XML에서는 `#{memberId}`와 `#{post.content}`로 구분하여 바인딩함.
- 단일 기본형/문자열 파라미터를 전달할 때
  - 단일 값은 `@Param`이 없어도 XML의 `#{}`에 들어오는 값이 자동으로 1:1 매핑되지만, 코드의 가독성과 명확성을 위해 `@Param("id") Long id` 형태로 명시하는 것을 권장함.
- 2개 이상의 매개변수 또는 컬렉션(List, Set)을 전달할 때
  - 자바 컴파일러의 매개변수 이름 소실 문제를 방지하고 XML과의 정확한 바인딩을 위해 반드시 `@Param("keyword")`, `@Param("memberId")`, `@Param("idList")`처럼 파라미터 이름을 선언해야 함.

### 1.4.2 매개변수 바인딩 문법: `#{}` vs `${}`
- `#{}` (PreparedStatement 바인딩)
  - 파라미터 값이 SQL 문장에 물음표(?) 파라미터로 치환되어 전달되므로 값에 따옴표가 자동 부착되고 SQL Injection [^4] 공격을 방지함.
  - 일반적인 모든 데이터 조건 조회, 등록, 수정, 삭제 시 필수적으로 사용함.
- `${}` (문자열 직접 치환)
  - 파라미터 값이 SQL 문장에 따옴표 없이 그대로 치환되어 삽입됨.
  - 사용자 입력값을 그대로 넣을 경우 SQL Injection 취약점이 발생하므로, 동적 테이블명이나 정렬 컬럼명(`ORDER BY ${sortColumn}`)을 안전하게 지정할 때를 제외하고는 사용을 지양.

- PostMapper 인터페이스 (src/main/java/net/likelion/bebc25/sns/mapper/PostMapper.java)
  ```java
  package net.likelion.bebc25.sns.mapper;

  import net.likelion.bebc25.sns.dto.PostCreateDto;
  import net.likelion.bebc25.sns.dto.PostResponseDto;
  import org.apache.ibatis.annotations.Mapper;
  import org.apache.ibatis.annotations.Param;

  import java.util.List;

  @Mapper
  public interface PostMapper {

      // 1. 단일 DTO 바인딩 (@Param 생략)
      void save(PostCreateDto post);

      // 2. 단일 기본형 바인딩 (@Param 명시)
      PostResponseDto findById(@Param("id") Long id);

      // 3. 단일 기본형 파라미터 기반 목록 조회
      List<PostResponseDto> findByMemberId(@Param("memberId") Long memberId);

      // 4. 다중 파라미터 바인딩 (@Param 필수)
      void update(@Param("id") Long id, @Param("content") String content, @Param("imageUrl") String imageUrl);

      // 5. 단일 기본형 단건 삭제
      void deleteById(@Param("id") Long id);
  }
  ```

- PostMapper.xml 파일 (src/main/resources/mapper/PostMapper.xml)
  ```xml
  <?xml version="1.0" encoding="UTF-8" ?>
  <!DOCTYPE mapper
          PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
          "https://mybatis.org/dtd/mybatis-3-mapper.dtd">

  <mapper namespace="net.likelion.bebc25.sns.mapper.PostMapper">

      <!-- 1. 단일 DTO 등록 및 생성 키 바인딩 -->
      <insert id="save" parameterType="PostCreateDto" useGeneratedKeys="true" keyProperty="id">
          INSERT INTO post (member_id, content, image_url, created_at, updated_at)
          VALUES (#{memberId}, #{content}, #{imageUrl}, NOW(), NOW())
      </insert>

      <!-- 2. 단일 기본형 단건 조회 바인딩 -->
      <select id="findById" parameterType="long" resultType="PostResponseDto">
          SELECT id, member_id, content, image_url, created_at, updated_at
          FROM post
          WHERE id = #{id}
      </select>

      <!-- 3. 단일 기본형 목록 조회 바인딩 -->
      <select id="findByMemberId" parameterType="long" resultType="PostResponseDto">
          SELECT id, member_id, content, image_url, created_at, updated_at
          FROM post
          WHERE member_id = #{memberId}
          ORDER BY id DESC
          LIMIT 10
      </select>

      <!-- 4. 다중 파라미터 수정 바인딩 -->
      <update id="update">
          UPDATE post
          SET content = #{content},
              image_url = #{imageUrl},
              updated_at = NOW()
          WHERE id = #{id}
      </update>

      <!-- 5. 단일 기본형 단건 삭제 바인딩 -->
      <delete id="deleteById" parameterType="long">
          DELETE FROM post
          WHERE id = #{id}
      </delete>

  </mapper>
  ```

- 매퍼 XML 주요 태그 속성 요약

| 속성명 | 적용 태그 | 주요 역할 및 동작 설명 |
| :--- | :--- | :--- |
| `id` | 전체 (`select`, `insert`, `update`, `delete`) | 매퍼 인터페이스의 메서드명과 1:1 매핑되는 고유 식별자. |
| `parameterType` | 전체 | SQL 문에 전달되는 파라미터의 자바 타입(패키지 경로 또는 별칭). (생략 가능) |
| `resultType` | `select` | 조회 결과 1개 행(Row)을 매핑할 자바 객체 타입(Record, DTO, String, Long 등). |
| `resultMap` | `select` | `<association>`, `<collection>` 등으로 복합 조인 규칙을 정의한 별도의 `<resultMap id="...">` 식별자 참조. |
| `useGeneratedKeys` | `insert`, `update` | MySQL의 AUTO_INCREMENT처럼 데이터베이스가 자동 생성한 기본키(PK) 값을 JDBC `getGeneratedKeys()`로 가져올지 여부 (`true` / `false`). |
| `keyProperty` | `insert`, `update` | `useGeneratedKeys="true"`로 가져온 자동 생성 PK 값을 파라미터 객체의 어떤 필드에 세팅할지 지정 (예: `keyProperty="id"`). |

### 1.5.1 1:1 계층적 복합 객체 매핑 (`<resultMap>`)
- 여러 테이블을 조인(JOIN)하여 계층적 복합 객체(1:1 단일 객체 매핑, 1:N 컬렉션 매핑)를 조립할 때는 `<resultMap>` 태그를 사용함.

- 매퍼 XML (src/main/resources/mapper/PostMapper.xml)
  ```xml
  <mapper namespace="net.likelion.bebc25.sns.mapper.PostMapper">

      ...

      <!-- 6. 3개 테이블 조인 쿼리 -->
      <select id="findPostDetailById" parameterType="long" resultMap="PostDetailResultMap">
          SELECT 
              p.id AS post_id,
              p.content AS post_content,
              p.image_url AS post_image_url,
              p.created_at AS post_created_at,
              m.id AS member_id,
              m.nickname AS member_nickname,
              m.profile_image AS member_profile_image,
              c.id AS comment_id,
              c.member_id AS commenter_id,
              cm.nickname AS commenter_nickname,
              c.content AS comment_content,
              c.created_at AS comment_created_at
          FROM post p
          INNER JOIN member m ON p.member_id = m.id
          LEFT JOIN comment c ON p.id = c.post_id
          LEFT JOIN member cm ON c.member_id = cm.id
          WHERE p.id = #{id}
          ORDER BY c.id ASC
          LIMIT 10
      </select>

      <resultMap id="PostDetailResultMap" type="PostDetailResponseDto">
          <id property="id" column="post_id" />
          <result property="content" column="post_content" />
          <result property="imageUrl" column="post_image_url" />
          <result property="createdAt" column="post_created_at" />

          <!-- 작성자 회원 정보 1:1 매핑 (<association>) -->

          <!-- 댓글 목록 1:N 매핑 (<collection>) -->

      </resultMap>

  </mapper>
  ```

  - `<resultMap>` 태그 속성
    - `id`: 해당 ResultMap의 고유 식별자 이름으로, `<select resultMap="...">`에서 지정하여 매핑 규칙을 적용함.
    - `type`: 최종적으로 조립된 결과 데이터를 담아 반환할 최상위 자바 DTO 객체 타입 (예: `PostDetailResponseDto`).
  - `<resultMap>` 내부 매핑 태그 및 속성
    - `<id>`: 기본키(PK, 식별자) 컬럼 매핑 태그. 객체 인스턴스의 고유성을 식별하여 조인 시 중복 객체 생성을 방지하고 메모리 조립 성능을 최적화함.
    - `<result>`: 기본키 이외의 일반 데이터 컬럼과 DTO 필드를 1:1 매핑하는 태그.
    - `property`: 컬럼 데이터가 매핑되어 저장될 자바 DTO 객체의 실제 필드명.
    - `column`: SELECT 조회 결과의 데이터베이스 컬럼명 또는 AS 별칭.

- PostMapper 인터페이스 메서드 추가 (src/main/java/net/likelion/bebc25/sns/mapper/PostMapper.java)

### 1.5.2 1:1 단일 객체 매핑 (`<association>`)
- 게시글 상세 조회 시 게시글(`post`) 정보에 작성자(`member`)의 요약 정보(`id`, `nickname`, `profileImage`)를 함께 조립하여 반환할 때 `<association>` 태그를 사용함.
- `MemberResponseDto`가 불변 `record`인 경우 Setter가 존재하지 않으므로, `<constructor>` 태그와 `<idArg>`, `<arg>`를 사용하여 정규 생성자 인자에 컬럼 값을 매핑함.
- `<association>` 태그 속성
  - `property`: 상위 DTO 내 필드명을 지정함.
  - `javaType`: 1:1로 매핑되는 단일 하위 객체의 자바 Record 타입 (예: `MemberResponseDto`).

- 작성자 1:1 매핑 XML (src/main/resources/mapper/PostMapper.xml)
  ```xml
  <!-- 작성자 회원 정보 1:1 매핑 (<association>) -->
  <association property="author" javaType="MemberResponseDto">
      <constructor>
          <idArg column="member_id" javaType="Long" />
          <arg column="member_nickname" javaType="String" />
          <arg column="member_profile_image" javaType="String" />
      </constructor>
  </association>
  ```

### 1.5.3 1:N 컬렉션 매핑 (`<collection>`)
- 하나의 게시글에 달린 여러 개의 댓글 목록(`List<CommentResponseDto>`)을 한 번의 쿼리로 함께 매핑할 때 `<collection>` 태그를 사용함.
- 컬렉션 원소인 `CommentResponseDto`가 불변 `record`인 경우 `<constructor>` 태그를 통해 생성자 인자 순서와 타입에 맞추어 매핑함.
- `<collection>` 태그 속성
  - `property`: 상위 DTO 내 리스트 필드명을 지정함.
  - `ofType`: 1:N으로 매핑되는 컬렉션(List)의 개별 원소로 들어갈 자바 Record 타입.
  - `javaType`: 컬렉션을 담아둘 자바 컬렉션 구현체 타입 (예: `ArrayList`).

  ```java
  // 11. 공통 SQL 조각 재사용 조회 (<sql>, <include>)
  PostResponseDto findByIdWithInclude(@Param("id") Long id);
  ```

### 1.6.1 `<where>`와 `<if>` 태그를 활용한 다중 조건 검색
- 검색 조건 DTO(`PostSearchCondition`)에 담긴 필드 값의 존재 유무에 따라 WHERE 절을 유연하게 생성함.
- `<where>` 태그는 조건문이 하나라도 참일 때만 `WHERE` 키워드를 삽입하고, 조건문 맨 앞에 오는 불필요한 `AND`나 `OR` 키워드를 자동으로 제거함.

  ```xml
  <!-- 7. 다중 조건 동적 검색 쿼리 -->
  <select id="searchPosts" parameterType="PostSearchCondition" resultType="PostResponseDto">
      SELECT id, member_id, content, image_url, created_at, updated_at
      FROM post
      <where>
          <if test="keyword != null and keyword != ''">
              AND content LIKE CONCAT('%', #{keyword}, '%')
          </if>
          <if test="memberId != null">
              AND member_id = #{memberId}
          </if>
          <if test="targetMemberIds != null and !targetMemberIds.isEmpty()">
              AND member_id IN
              <foreach item="targetId" collection="targetMemberIds" open="(" separator="," close=")">
                  #{targetId}
              </foreach>
          </if>
      </where>
      ORDER BY id DESC
      LIMIT 10
  </select>
  ```

### 1.6.2 `<choose>`, `<when>`, `<otherwise>`를 활용한 동적 정렬 분기
- 자바의 switch-case 문처럼 전달받은 `sortOrder` 값에 따라 ORDER BY 정렬 기준을 안전하게 분기함.

  ```xml
  <!-- 8. 동적 정렬 분기 조회 -->
  <select id="findPostsWithSort" parameterType="PostSearchCondition" resultType="PostResponseDto">
      SELECT id, member_id, content, image_url, created_at, updated_at
      FROM post
      <choose>
          <when test="sortOrder == 'POPULAR'">
              ORDER BY like_count DESC, id DESC
          </when>
          <otherwise>
              ORDER BY id DESC
          </otherwise>
      </choose>
      LIMIT 10
  </select>
  ```

### 1.6.3 `<set>` 태그를 활용한 동적 부분 수정 (Dynamic UPDATE)
- 수정이 요청된 필드만 선택적으로 UPDATE하며, 마지막 컬럼 뒤에 남는 불필요한 쉼표(,)를 자동으로 제거해 줌.

  ```xml
  <!-- 9. 동적 부분 수정 (Dynamic UPDATE) -->
  <update id="updateSelective" parameterType="map">
      UPDATE post
      <set>
          <if test="content != null">
              content = #{content},
          </if>
          <if test="imageUrl != null">
              image_url = #{imageUrl},
          </if>
          updated_at = NOW()
      </set>
      WHERE id = #{id}
  </update>
  ```

### 1.6.4 `<foreach>` 태그를 활용한 컬렉션 반복 (IN 절 및 일괄 삭제)
- List, Set 등의 컬렉션을 반복 순회하여 `IN (1, 2, 3)` 형태의 SQL 절을 동적으로 생성함.

  ```xml
  <!-- 10. 다중 ID 일괄 삭제 (동적 foreach) -->
  <delete id="deleteByIds">
      DELETE FROM post
      WHERE id IN
      <foreach item="targetId" collection="idList" open="(" separator="," close=")">
          #{targetId}
      </foreach>
  </delete>
  ```

### 1.6.5 `<sql>`과 `<include>` 태그를 활용한 쿼리 조각 재사용
- 자주 중복되는 컬럼 목록이나 공통 조건절을 `<sql id="...">`로 정의하고, 필요한 곳에서 `<include refid="...">`로 재사용하여 유지보수성을 높임.

  ```xml
  <!-- 공통 컬럼 조각 정의 -->
  <sql id="postColumns">
      id, member_id, content, image_url, created_at, updated_at
  </sql>

  <!-- 11. 공통 조각 재사용 -->
  <select id="findByIdWithInclude" parameterType="long" resultType="PostResponseDto">
      SELECT <include refid="postColumns" />
      FROM post
      WHERE id = #{id}
      LIMIT 10
  </select>
  ```

### 2.3.3 매퍼 XML에 ResultMap 및 3중 조인 쿼리 추가
- PostMapper.xml에 ResultMap 및 조인 쿼리 추가 (src/main/resources/mapper/PostMapper.xml)
  ```xml
  <!-- ResultMap 복합 객체 조립 정의 (1:1 작성자, 1:N 댓글 목록) -->
  <resultMap id="PostDetailResultMap" type="PostDetailResponseDto">
      <id property="id" column="post_id" />
      <result property="content" column="post_content" />
      <result property="imageUrl" column="post_image_url" />
      <result property="createdAt" column="post_created_at" />

      <!-- 작성자 회원 정보 1:1 매핑 -->
      <association property="author" javaType="MemberResponseDto">
          <constructor>
              <idArg column="member_id" javaType="Long" />
              <arg column="member_nickname" javaType="String" />
              <arg column="member_profile_image" javaType="String" />
          </constructor>
      </association>

      <!-- 댓글 목록 1:N 매핑 -->
      <collection property="comments" ofType="CommentResponseDto" javaType="ArrayList">
          <constructor>
              <idArg column="comment_id" javaType="Long" />
              <arg column="commenter_id" javaType="Long" />
              <arg column="commenter_nickname" javaType="String" />
              <arg column="comment_content" javaType="String" />
              <arg column="comment_created_at" javaType="java.time.LocalDateTime" />
          </constructor>
      </collection>
  </resultMap>

  <!-- 7. 게시글 상세 + 작성자 + 댓글 3중 조인 쿼리 -->
  <select id="findPostDetailById" parameterType="long" resultMap="PostDetailResultMap">
      SELECT 
          p.id AS post_id,
          p.content AS post_content,
          p.image_url AS post_image_url,
          p.created_at AS post_created_at,
          m.id AS member_id,
          m.nickname AS member_nickname,
          m.profile_image AS member_profile_image,
          c.id AS comment_id,
          c.member_id AS commenter_id,
          cm.nickname AS commenter_nickname,
          c.content AS comment_content,
          c.created_at AS comment_created_at
      FROM post p
      INNER JOIN member m ON p.member_id = m.id
      LEFT JOIN comment c ON p.id = c.post_id
      LEFT JOIN member cm ON c.member_id = cm.id
      WHERE p.id = #{id}
      ORDER BY c.id ASC
      LIMIT 10
  </select>
  ```

  ```java
          assertThat(detail.getAuthor().id()).isNotNull();
          assertThat(detail.getAuthor().nickname()).isNotNull();

          // 1:N 댓글 목록 컬렉션 매핑 검증 (<collection>)

      }
  ```

# 3. 스프링 선언적 트랜잭션

- 트랜잭션 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/04.database-2.md#6-트랜잭션의-이해

## 3.1 스프링 트랜잭션 추상화

### 3.1.1 데이터 접근 기술별 트랜잭션 관리 방식과 한계
- 데이터 접근 기술마다 트랜잭션을 제어하는 자바 API와 사용 방식이 제각각 다름.
  - JDBC / MyBatis: `connection.setAutoCommit(false)`, `connection.commit()`, `connection.rollback()`
  - JPA: `entityManager.getTransaction().begin()`, `transaction.commit()`, `transaction.rollback()`
  - Hibernate: `session.beginTransaction()`, `tx.commit()`, `tx.rollback()`
- 스프링이 제공하는 기술별 전용 트랜잭션 매니저 클래스
  - 스프링은 이처럼 서로 다른 외부 기술들의 트랜잭션을 제어할 수 있도록 기술별 전용 구현 클래스들을 제공함.
    - `DataSourceTransactionManager`: 순수 JDBC, JdbcTemplate, Spring Data JDBC, MyBatis 전용
    - `JpaTransactionManager`: JPA 엔티티 매니저 연동 전용
    - `HibernateTransactionManager`: 하이버네이트 세션 연동 전용
- 개별 구현 클래스 직접 의존 시의 한계
  - 서비스 계층의 비즈니스 코드가 특정 트랜잭션 매니저 클래스(예: `DataSourceTransactionManager`)에 직접 의존하면, 향후 데이터 접근 기술을 변경(예: MyBatis ➔ JPA)할 때 서비스 계층의 트랜잭션 제어 코드를 수정해야 하는 문제가 남음.

### 3.1.2 PlatformTransactionManager를 통한 단일 표준 추상화
- 스프링은 이 개별 구현 클래스들을 다시 하나의 최상위 표준 인터페이스인 `PlatformTransactionManager`로 통합 추상화함.

```
                         [PlatformTransactionManager 인터페이스]
                                          ▲
             ┌────────────────────────────┼────────────────────────────┐
             │                            │                            │
[DataSourceTransactionManager]   [JpaTransactionManager]    [HibernateTransactionManager]
(JDBC / JdbcTemplate / MyBatis /        (JPA 전용)                  (하이버네이트)
       Spring Data JDBC)
```

- 트랜잭션 추상화가 제공하는 핵심 이점
  - 기술 독립성 및 단일 제어: 서비스 계층은 하위의 구체적인 트랜잭션 매니저 클래스를 직접 다루지 않고 최상위 인터페이스에만 의존하므로, `@Transactional` 선언 하나만으로 모든 데이터 접근 기술의 트랜잭션을 동일하게 제어할 수 있음.
  - OCP(개방-폐쇄 원칙) [^5] 준수: 데이터 접근 기술을 MyBatis에서 JPA 등으로 교체하더라도 서비스 계층의 비즈니스 로직과 `@Transactional` 코드는 단 한 줄도 수정할 필요가 없음.
  - 스프링 부트 자동 구성(Auto-Configuration): 빌드 의존성(`starter`)에 따라 적절한 트랜잭션 매니저 구현체 빈을 프레임워크가 자동으로 생성하여 스프링 컨테이너에 등록함.
- 스레드 로컬 기반 커넥션 동기화 (TransactionSynchronizationManager)
  - 스프링은 멀티스레드 환경에서 각 스레드마다 독립적인 DB 커넥션을 유지하기 위해 `TransactionSynchronizationManager`(스레드 로컬(ThreadLocal) [^6] 저장소)를 사용함.
  - 트랜잭션 시작 시 획득한 커넥션을 스레드 로컬에 보관하고, 서비스 내부에서 호출되는 DAO, Mapper들이 동일한 커넥션을 꺼내 쓰도록 보장함.
  - 여러 매퍼 메서드나 JdbcTemplate을 동일한 서비스 메서드 안에서 호출하더라도 하나의 트랜잭션으로 묶이는 이유.

## 3.2 @Transactional 선언과 AOP 프록시 동작 메커니즘

### 3.2.1 선언적 트랜잭션의 장점 및 적용 위치
- 과거 트랜잭션 코드를 직접 자바 소스코드에 작성하던 프로그래밍 방식(Programmatic Transaction)과 달리, `@Transactional` 어노테이션을 메서드나 클래스에 선언하기만 하면 프레임워크가 트랜잭션 시작, 커밋, 롤백을 자동 처리함.
- 비즈니스 핵심 로직과 트랜잭션 인프라 코드를 명확히 분리하여 단일 책임 원칙(SRP) [^7] 을 준수함.

### 3.2.2 AOP 프록시를 통한 트랜잭션 경계 제어 메커니즘
- 트랜잭션 경계(Transaction Boundary): 트랜잭션이 시작(Begin)되어 커밋(Commit) 또는 롤백(Rollback)으로 종결되는 논리적인 작업 범위를 의미하며, AOP [^8] 프록시가 이 경계의 시작과 끝을 가로채어 트랜잭션을 자동 제어함.
- 컨트롤러가 `@Transactional`이 부여된 서비스 빈을 호출하면, 실제 타깃 객체가 아닌 스프링이 동적으로 생성한 트랜잭션 프록시(Proxy) 객체가 호출을 인터셉트함.

```
    [컨트롤러]
        │
        ▼
[트랜잭션 AOP 프록시] ─── (1) PlatformTransactionManager.getTransaction() ───> 커넥션 획득 & setAutoCommit(false)
        │
        ├─── (2) 타깃 서비스 비즈니스 메서드 실행 ───> (MyBatis / JDBC 작업 수행)
        │
        ▼
[트랜잭션 AOP 프록시] ─── (3) 정상 종료 시: commit() / 예외 발생 시: rollback() ───> 커넥션 자원 반납
```

## 3.3 트랜잭션 전파 속성과 격리 수준

### 3.3.1 전파 속성 (Propagation)
- 이미 트랜잭션이 진행 중인 상태에서 또 다른 트랜잭션 메서드가 호출되었을 때, 기존 트랜잭션에 참여할지 혹은 새로운 독립 트랜잭션을 시작할지 결정하는 정책.

| 전파 속성 | 동작 방식 | 주요 활용처 |
| :--- | :--- | :--- |
| `REQUIRED` (기본값) | 기존 트랜잭션이 존재하면 참여하고, 없으면 새로운 트랜잭션을 생성함 | 대부분의 일반적인 비즈니스 로직 |
| `REQUIRES_NEW` | 항상 독립적인 새로운 트랜잭션을 시작함 (기존 트랜잭션은 일시 보류됨) | 실패해도 메인 트랜잭션에 영향을 주지 않아야 하는 감사 로그, 알림 발송 |
| `SUPPORTS` | 기존 트랜잭션이 있으면 참여하고, 없으면 트랜잭션 없이 일반 모드로 동작함 | 단순 데이터 조회 작업 |
| `NOT_SUPPORTED` | 기존 트랜잭션이 있어도 보류시키고, 트랜잭션 없이 동작함 | 외부 API 연동 등 장시간 블로킹 작업 |
| `MANDATORY` | 반드시 기존 트랜잭션이 존재해야 하며, 없으면 예외(`IllegalTransactionStateException`) 발생 | 독립 실행을 금지하는 하위 컴포넌트 |
| `NEVER` | 트랜잭션이 없어야 하며, 기존 트랜잭션이 존재하면 예외 발생 | 트랜잭션 비허용 작업 |

### 3.3.2 격리 수준 (Isolation)
- 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/04.database-2.md#625-데이터베이스-격리-수준-isolation-level

- 여러 트랜잭션이 동시에 실행될 때 특정 트랜잭션이 다른 트랜잭션의 변경 데이터를 볼 수 있는 허용 범위를 규정함.

| 격리 수준 | 동시성 처리 성능 | 격리 안전성 | 발생 가능한 이상 현상 |
| :--- | :--- | :--- | :--- |
| `READ_UNCOMMITTED` | 가장 빠름 | 가장 낮음 | Dirty Read, Non-Repeatable Read, Phantom Read |
| `READ_COMMITTED` | 우수함 | 보통 | Non-Repeatable Read, Phantom Read |
| `REPEATABLE_READ` (MySQL InnoDB 기본값) | 보통 | 높음 | Phantom Read (InnoDB MVCC 환경에서는 대부분 방지) |
| `SERIALIZABLE` | 가장 느림 | 우수함 | 모든 이상 현상 방지 (트랜잭션 순차 직렬 실행) |

- 동시성 격리 이상 현상
  - Dirty Read: 아직 커밋되지 않은 다른 트랜잭션의 임시 변경 데이터를 읽는 현상.
  - Non-Repeatable Read: 동일한 트랜잭션 내에서 같은 쿼리를 두 번 실행했을 때, 중간에 다른 트랜잭션이 데이터를 수정/커밋하여 조회 결과값이 달라지는 현상.
  - Phantom Read: 동일한 범위 조건으로 두 번 조회했을 때, 중간에 다른 트랜잭션이 새로운 행을 삽입/삭제하여 결과 행 수가 달라지는 현상.

### 3.3.3 readOnly 속성을 통한 조회 성능 최적화
- 데이터 변경(INSERT, UPDATE, DELETE) 없이 단순 조회만 수행하는 메서드에는 `@Transactional(readOnly = true)`를 선언함.
- 최적화 효과
  - JDBC 드라이버 및 DB 커넥션이 읽기 전용 모드로 전환되어 불필요한 쓰기 락(Lock) 경합 방지.
  - JPA 및 ORM 환경에서 변경 감지(Dirty Checking)를 위한 스냅샷 객체를 메모리에 보관하지 않아 CPU 및 메모리 자원 절약.
  - 데이터 변경 쿼리 실행 시 예외를 발생시켜 의도치 않은 데이터 조작을 차단.

## 3.4 @Transactional 실무 사용법과 권장 설정
- 일반적으로 트랜잭션 경계는 비즈니스 로직의 단위가 시작되고 종결되는 서비스(Service) 계층에 적용함.

- 기본 선언 방식
  - 스프링의 `@Transactional`은 별도의 옵션을 주지 않아도 가장 표준적이고 안전한 기본값(전파: REQUIRED, 격리수준: DB 기본값)으로 동작함.
  - 데이터 등록, 수정, 삭제 작업을 수행하는 비즈니스 메서드 상단에 `@Transactional`을 선언.

- 적용 위치 및 우선순위 규칙
  - 클래스 레벨 선언: 클래스 내의 모든 `public` 메서드에 기본 트랜잭션이 적용됨.
  - 메서드 레벨 선언: 개별 메서드에 선언되며, 클래스 레벨보다 더 높은 우선순위를 가짐 (클래스 설정을 오버라이드함).

- 실무에서 주로 사용하는 핵심 속성 2가지
  - `readOnly = true` (조회 성능 최적화): 데이터 변경이 없는 단순 조회 메서드에 선언하며, 불필요한 DB 쓰기 락(Lock)을 방지하고 메모리 자원을 절약함.
  - `rollbackFor = Exception.class` (예외 롤백 보장): 스프링은 기본적으로 언체크 예외(`RuntimeException`)만 자동 롤백하고 체크 예외(`Exception`)는 커밋하므로, 실무에서는 모든 예외 상황에서 안전하게 롤백되도록 `rollbackFor = Exception.class`를 명시함.
    - Exception 참고: https://github.com/BEBC-25/java-yong/blob/main/docs/05.java_advanced.md#12-예외-클래스의-계층-구조

- 실무 모범 패턴
  - 서비스 클래스 상단에 `@Transactional(readOnly = true)`를 선언하여 기본 조회 성능을 최적화하고, 데이터 변경(INSERT, UPDATE, DELETE)이 필요한 메서드에만 `@Transactional(rollbackFor = Exception.class)`를 부여함.

```java
@Service
@Transactional(readOnly = true) // 클래스 전체(모든 메서드에 적용): 기본 조회 전용 모드로 성능 최적화
public class PostService {

    private final PostMapper postMapper;
    private final LikeBookmarkMapper likeBookmarkMapper;

    public PostService(PostMapper postMapper, LikeBookmarkMapper likeBookmarkMapper) {
        this.postMapper = postMapper;
        this.likeBookmarkMapper = likeBookmarkMapper;
    }

    // 1. 클래스의 기본값 readOnly = true 적용 (단순 조회)
    public PostResponseDto getPost(Long id) {
        return postMapper.findById(id);
    }

    // 2. 기본 @Transactional 적용: 별도 옵션 없이 기본값(readOnly = false, 쓰기 허용)으로 동작
    @Transactional
    public void createPost(PostCreateDto dto) {
        postMapper.insertPost(dto);
    }

    // 3. @Transactional(rollbackFor = Exception.class) 적용: 다중 작업 묶음 및 모든 예외 롤백 보장
    @Transactional(rollbackFor = Exception.class)
    public void addLike(Long memberId, Long postId) {
        // 1) 좋아요 테이블에 등록
        likeBookmarkMapper.insertLike(memberId, postId);

        // 2) post 테이블의 like_count 1 증가 (2번 작업 중 오류 발생 시 1번 좋아요 등록도 함께 롤백됨)
        postMapper.increaseLikeCount(postId);
    }
}
```

# 4. 서비스 계층 선언적 트랜잭션 실습

## 4.1 트랜잭션 적용 시나리오: 좋아요 토글
- 사용자가 좋아요 버튼을 클릭할 때마다 현재 상태를 반전(미등록 시 등록, 기등록 시 취소)시키는 토글(Toggle) 시나리오.
- 작업 도중 예외가 발생하면 앞선 모든 데이터 변경 연산이 원자적으로 롤백되어 데이터 불일치를 방지함.

### 4.1.1 좋아요 토글 단계별 실행 흐름
1. 대상 게시글 존재 여부 검증 (`PostMapper.findById`)
2. 현재 회원의 기존 좋아요 등록 여부 조회 (`PostLikeMapper.countLike`)
3. 조회 결과에 따른 상태 분기 및 복합 연산 실행
  - 미등록 상태인 경우: `post_like` 테이블에 좋아요 등록(`insertLike`) 및 `post` 테이블의 `like_count` 1 증가(`increaseLikeCount`)를 원자적으로 수행하고, 갱신된 결과 DTO(`liked: true`, 최신 `likeCount`) 반환
  - 기등록 상태인 경우: `post_like` 테이블에서 좋아요 삭제(`deleteLike`) 및 `post` 테이블의 `like_count` 1 감소(`decreaseLikeCount`)를 원자적으로 수행하고, 갱신된 결과 DTO(`liked: false`, 최신 `likeCount`) 반환

## 4.2 매퍼 설계 원칙: 도메인 관점과 테이블 책임 분리

### 4.2.1 도메인 관점 (통합 매퍼)
- 특징: 게시글(Post)이라는 핵심 도메인 개체와 생명주기를 함께하는 부속 데이터(`post_like`, `post_comment` 등)의 쿼리를 `PostMapper` 단일 파일에 모두 모아 관리함.
- 장점: 관련 기능의 쿼리가 한곳에 집중되어 파일 개수가 적고 초기 도메인 흐름 파악이 수월함.
- 단점: 기능이 늘어날수록 단일 XML 파일이 지나치게 길어지고, 좋아요나 댓글 같은 다른 테이블의 쿼리를 고치다가 게시글 기본 쿼리에 의도치 않은 영향을 줄 수 있어 코드 관리가 복잡해짐.

### 4.2.2 테이블 책임 분리 관점 (독립 매퍼)
- 특징: 데이터베이스의 개별 물리 테이블 1개당 매퍼 1개를 원칙으로 하여, `post` 테이블 전담 매퍼(`PostMapper`)와 `post_like` 테이블 전담 매퍼(`PostLikeMapper`)로 명확히 분리함.
- 장점: 단일 책임 원칙(SRP) [^7]<sup>2</sup> 을 준수하여 각 매퍼가 특정 테이블에 대한 데이터 접근만 전담하므로 결합도가 낮아지고 유지보수 및 모듈화가 용이함.
- 단점: 관리해야 할 매퍼 인터페이스와 XML 매퍼 파일의 총 개수가 늘어남.

## 4.3 PostLikeMapper 인터페이스 및 XML 구현

  ```java
      // 특정 회원의 게시글 좋아요 등록 여부 조회 (0 또는 1 반환)
  ```

  ```java
  @Service
  @Transactional(readOnly = true)
  public class PostLikeServiceImpl implements PostLikeService {

      private final PostMapper postMapper;
      private final PostLikeMapper postLikeMapper;

      public PostLikeServiceImpl(PostMapper postMapper, PostLikeMapper postLikeMapper) {
          this.postMapper = postMapper;
          this.postLikeMapper = postLikeMapper;
      }

      @Override
      @Transactional(rollbackFor = Exception.class)
      public LikeToggleResponseDto toggleLike(Long memberId, Long postId) {
          // 1. 대상 게시글 존재 여부 검증 (PostMapper)
          PostResponseDto post = postMapper.findById(postId);
          if (post == null) {
              throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + postId);
          }

          // 2. 현재 회원의 좋아요 등록 여부 확인 (PostLikeMapper)
          boolean isLiked = postLikeMapper.countLike(memberId, postId) > 0;

          if (isLiked) {
              // 기등록 상태: 좋아요 취소 (삭제) 및 like_count 1 감소
              postLikeMapper.deleteLike(memberId, postId);
              postMapper.decreaseLikeCount(postId);
              return new LikeToggleResponseDto(false, post.likeCount() - 1);
          } else {
              // 미등록 상태: 좋아요 등록 및 like_count 1 증가
              postLikeMapper.insertLike(memberId, postId);
              postMapper.increaseLikeCount(postId);
              return new LikeToggleResponseDto(true, post.likeCount() + 1);
          }
      }
  }
  ```

## 4.6 트랜잭션 롤백 테스트 및 무결성 검증
- 통합 테스트 환경에서 분리된 두 매퍼 간의 연동과 트랜잭션 원자성을 검증함.
- `@MockitoSpyBean`
  - 스프링 컨텍스트에 등록된 실제 빈(Bean)을 그대로 유지하면서, 원하는 특정 메서드만 가짜 동작(모킹)을 수행하거나 강제 예외를 던지도록 감싸는 테스트 어노테이션.
  - 정상적인 DB 조회/등록 동작은 실제 빈에 그대로 위임하고, 2단계인 `increaseLikeCount` 메서드 호출 시점에만 인위적인 런타임 예외를 발생시켜 시스템 장애 상황을 시뮬레이션함.
  - 검증 목적: 2단계에서 예외가 발생했을 때 `@Transactional`에 의해 앞선 1단계(좋아요 등록) 데이터까지 원자적으로 함께 롤백되는지 확인.
- `Propagation.NOT_SUPPORTED` 전파 속성
  - 동작 메커니즘: 이미 진행 중인 활성 트랜잭션이 존재하면 이를 일시 중단(Suspend)시키고, 트랜잭션이 적용되지 않는 비트랜잭션(Non-Transactional) 상태로 메서드를 실행함.
  - 적용 이유: 클래스 레벨의 `@Transactional`에 의해 생성된 부모 트랜잭션을 일시 중단하여, 서비스 메서드가 부모 트랜잭션에 참여하지 않고 독자적인 트랜잭션을 시작하도록 격리함. 그 결과 서비스 계층에서 예외가 발생하는 즉시 스스로 물리적 롤백을 완료하므로 DB의 롤백 결과를 정확히 검증할 수 있음.

## 5.3 서비스 구현 클래스 및 비즈니스 예외 처리
- `PostMapper`를 주입받아 데이터 접근 연산을 수행하며, 읽기 전용 트랜잭션 최적화와 CUD 데이터 변경 트랜잭션을 분리하여 적용.
- 클래스 레벨에 `@Transactional(readOnly = true)`를 적용하여 기본 조회 성능을 최적화하고, 데이터 변경 메서드에만 쓰기 전용 `@Transactional`을 선언함.
- 수정 및 삭제 시 대상 게시글 존재 여부를 사전에 검증하여 데이터 무결성을 보호함.

- src/main/java/net/likelion/bebc25/sns/service/PostServiceImpl.java
  ```java
  package net.likelion.bebc25.sns.service;

  import net.likelion.bebc25.sns.dto.PostCreateDto;
  import net.likelion.bebc25.sns.dto.PostDetailResponseDto;
  import net.likelion.bebc25.sns.dto.PostResponseDto;
  import net.likelion.bebc25.sns.dto.PostSearchCondition;
  import net.likelion.bebc25.sns.dto.PostUpdateDto;
  import net.likelion.bebc25.sns.mapper.PostMapper;
  import org.springframework.stereotype.Service;
  import org.springframework.transaction.annotation.Transactional;

  import java.util.List;

  @Service
  @Transactional(readOnly = true)
  public class PostServiceImpl implements PostService {

      private final PostMapper postMapper;

      public PostServiceImpl(PostMapper postMapper) {
          this.postMapper = postMapper;
      }

      @Override
      @Transactional(rollbackFor = Exception.class)
      public Long createPost(PostCreateDto dto) {
          postMapper.save(dto);
          return dto.getId();
      }

      @Override
      public PostResponseDto getPostById(Long id) {
          PostResponseDto post = postMapper.findById(id);
          if (post == null) {
              throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + id);
          }
          return post;
      }

      @Override
      public PostDetailResponseDto getPostDetailById(Long id) {
          PostDetailResponseDto detail = postMapper.findPostDetailById(id);
          if (detail == null) {
              throw new IllegalArgumentException("존재하지 않는 게시글입니다. ID: " + id);
          }
          return detail;
      }

      @Override
      public List<PostResponseDto> searchPosts(PostSearchCondition condition) {
          return postMapper.searchPosts(condition);
      }

      @Override
      @Transactional(rollbackFor = Exception.class)
      public void updatePost(Long id, PostUpdateDto dto) {
          // 수정 대상 게시글 존재 여부 사전 검증
          if (postMapper.findById(id) == null) {
              throw new IllegalArgumentException("수정할 게시글이 존재하지 않습니다. ID: " + id);
          }
          postMapper.update(id, dto.content(), dto.imageUrl());
      }

      @Override
      @Transactional(rollbackFor = Exception.class)
      public void deletePost(Long id) {
          // 삭제 대상 게시글 존재 여부 사전 검증
          if (postMapper.findById(id) == null) {
              throw new IllegalArgumentException("삭제할 게시글이 존재하지 않습니다. ID: " + id);
          }
          postMapper.deleteById(id);
      }

      @Override
      @Transactional(rollbackFor = Exception.class)
      public void deletePosts(List<Long> idList) {
          if (idList == null || idList.isEmpty()) {
              throw new IllegalArgumentException("삭제할 게시글 ID 목록이 비어있습니다.");
          }
          postMapper.deleteByIds(idList);
      }
  }
  ```

# 각주
[^1]: 배치 스크립트(Batch Script): 사용자와의 실시간 상호작용 없이 대량의 데이터를 정해진 규칙과 순서에 따라 일괄 처리하는 자동화 프로그램
[^2]: 도메인 주도 설계(DDD, Domain-Driven Design): 복잡한 소프트웨어 개발 시 순수 비즈니스 도메인 모델과 도메인 로직을 핵심 중심에 두고 설계 및 구현을 일치시키는 개발 방법론
[^3]: 동적 프록시(Dynamic Proxy): 런타임 시점에 인터페이스를 기반으로 프레임워크가 구현 클래스 객체를 동적으로 생성하여 주입하는 기법
[^4]: SQL Injection: 입력 폼에 악의적인 SQL 문을 주입하여 데이터베이스를 비정상적으로 조작하거나 데이터를 탈취하는 공격 기법
[^5]: OCP(개방-폐쇄 원칙, Open-Closed Principle): 기존 코드를 변경하지 않고도 기능을 확장할 수 있어야 한다는 객체지향 설계 5대 원칙(SOLID) 중 하나
[^6]: 스레드 로컬(ThreadLocal): 다른 스레드와 공유되지 않고 오직 현재 실행 중인 단일 스레드 내부에서만 독립적으로 접근 및 유지되는 전용 저장 공간
[^7]: 단일 책임 원칙(SRP, Single Responsibility Principle): 객체는 단 하나의 변경 책임만을 가져야 한다는 객체지향 설계 5대 원칙(SOLID) 중 하나
[^8]: AOP(Aspect-Oriented Programming): 핵심 비즈니스 로직과 트랜잭션, 보안, 로깅 등 공통 관심사를 분리하여 모듈화하는 관점 지향 프로그래밍
