# 1. JPQL(Java Persistence Query Language)과 객체지향 쿼리

## 1.1 JPQL 정의 및 표준 SQL과의 차이점
- JPQL(Java Persistence Query Language)은 데이터베이스 테이블이 아닌 JPA 엔티티 객체를 대상으로 질의를 수행하는 객체지향 쿼리 언어.
- 특정 데이터베이스 벤더(MySQL, PostgreSQL, Oracle 등)의 SQL 문법에 종속되지 않고, 설정된 방언(Dialect)을 기반으로 실행 시점에 해당 데이터베이스 전용 SQL로 자동 번역됨.
- 객체지향 모델링을 온전히 유지하면서 복잡한 검색 쿼리를 처리할 수 있으며, 연관 엔티티의 객체 그래프 탐색 문법을 지원함.

### 1.1.1 JPQL과 표준 SQL의 핵심 차이점
- 질의 대상
  - SQL: 데이터베이스의 테이블명과 물리 컬럼명을 직접 대상으로 쿼리를 작성함.
  - JPQL: 자바 소스코드에 매핑된 엔티티 클래스명과 엔티티 필드(프로퍼티)명을 대상으로 쿼리를 작성함.
- 대소문자 구분 규칙: `SELECT`, `FROM`, `WHERE` 등 JPQL 예약어는 대소문자를 가리지 않으나, 엔티티 클래스명(`Post`)과 프로퍼티명(`likeCount`, `member`)은 자바 코드와 동일하게 대소문자를 엄격하게 구분함.
- 엔티티 별칭(Alias) 필수 선언: JPQL의 `FROM` 절에서는 대상 엔티티에 대한 별칭(예: `FROM Post p`)을 필수로 선언해야 하며, 프로퍼티 참조 시 해당 별칭을 통해 접근함 (`AS` 키워드는 생략 가능).

## 1.2 JPQL 기본 문법 구조와 객체 그래프 탐색
JPQL은 표준 SQL과 유사한 절(Clause) 구조를 제공하며 엔티티 객체 단위로 데이터를 조회함.

### 1.2.1 기본 쿼리 절 구조
- SELECT 절: 조회할 엔티티 또는 특정 속성을 지정함 (`SELECT p FROM Post p`).
- FROM 절: 조회 대상 엔티티 클래스명을 지정하며 별칭 선언이 필수 (`Post p`).
- WHERE 절: 필터링 조건을 지정하며 엔티티 필드명을 대상으로 비교 연산을 수행함 (`WHERE p.likeCount >= 10`).
- ORDER BY 절: 정렬 기준 필드를 지정함 (`ORDER BY p.id DESC`).

### 1.2.2 객체 그래프 탐색 기본 원리
- 점(`.`) 표기법을 사용하여 엔티티가 참조하고 있는 연관 객체의 필드에 직접 접근하는 방식.
- 단일 값 연관 경로 탐색: 게시글(`Post`) 엔티티를 조회하면서 연관된 작성자(`Member`)의 닉네임을 조건절에서 참조 가능 (`WHERE p.member.nickname = '하루'`).
- 기본 JPQL 작성 예시
  ```sql
  -- 작성자 닉네임이 '하루'이고 좋아요 수가 10 이상인 게시글을 ID 내림차순으로 정렬 조회
  SELECT p FROM Post p WHERE p.member.nickname = '하루' AND p.likeCount >= 10 ORDER BY p.id DESC
  ```

- 데이터베이스에서 실제 실행되는 변환 SQL
  ```sql
  -- p.member.nickname 탐색으로 인해 member 테이블과의 내부 조인(INNER JOIN)이 자동 생성됨
  SELECT
      p.id,
      p.content,
      p.image_url,
      p.like_count,
      p.member_id,
      p.created_at,
      p.updated_at
  FROM
      post p
  INNER JOIN
      member m ON p.member_id = m.id
  WHERE
      m.nickname = '하루'
      AND p.like_count >= 10
  ORDER BY
      p.id DESC
  ```

# 2. Spring Data JPA 쿼리 메서드와 페이징

## 2.1 메서드 이름 기반 쿼리 생성
리포지토리 인터페이스에 정해진 명명 규칙에 맞추어 메서드 이름을 선언하면, Spring Data JPA가 애플리케이션 기동 시점에 이름을 분석하여 적절한 JPQL을 자동으로 조립하고 데이터베이스 쿼리를 실행함.

### 2.1.1 쿼리 메서드 구조 및 파싱 메커니즘
메서드 이름은 주어부와 술어부(조건절)가 `By` 키워드를 기점으로 결합되는 규칙을 준수함.
- 주어부
  - `find...By`, `read...By`, `get...By`, `query...By`, `search...By`: 기본 엔티티 조회 쿼리 구성.
  - `count...By`: 조건에 부합하는 레코드 건수 반환 (`Long`).
  - `exists...By`: 조건에 부합하는 데이터 존재 여부 반환 (`boolean`).
  - `delete...By`, `remove...By`: 조건에 부합하는 데이터 삭제 쿼리 실행 (`Long` 또는 `void`).
  - 주어부 수식어 및 도메인 명사 활용
    - `Distinct`, `First<N>`, `Top<N>`을 추가하여 중복 제거 및 조회 결과 건수를 제한할 수 있음.
    - `findPostsBy...`, `findAllBy...`처럼 `By` 앞에 도메인 명사나 서술어를 덧붙여도 Spring Data JPA는 이를 단순 플레이스홀더로 인식하여 정상 처리함.
- 술어부 (조건절)
  - `By` 키워드 뒤에 선언되며 엔티티의 프로퍼티명과 연산자 키워드를 조합하여 `WHERE` 조건절을 생성함.
  - 연산자 키워드를 생략하면 동등 비교(`=`) 조건이 기본으로 적용됨.

### 2.1.2 지원 키워드 및 생성 쿼리 매핑

| 키워드 범주 | 메서드 이름 샘플 | 생성되는 JPQL 조건절 구문 |
| :--- | :--- | :--- |
| 포함 검색 | findByContentContaining(String keyword) | where p.content like %:keyword% |
| 대소 비교 | findByLikeCountGreaterThanEqual(int count) | where p.likeCount >= :count |
| 다중 조건 | findByContentContainingAndLikeCountGreaterThanEqual(String keyword, int count) | where p.content like %:keyword% and p.likeCount >= :count |
| 범위 검색 | findByCreatedAtBetween(LocalDateTime startDateTime, LocalDateTime endDateTime) | where p.createdAt between :startDateTime and :endDateTime |
| 목록 포함 | findByMemberIn(Collection<Member> members) | where p.member in (:members) |
| 정렬 | findByMemberIdOrderByCreatedAtDesc(Long memberId) | where p.member.id = :memberId order by p.createdAt desc |
| 개수 제한 | findFirst3ByOrderByLikeCountDesc() | order by p.likeCount desc limit 3 |
| 존재 여부 | existsByEmail(String email) | select case when count(m)>0 then true else false |
| 건수 집계 | countByMemberId(Long memberId) | select count(p) where p.member.id = :memberId |

#### 2) 테스트 케이스 작성
- src/test/java/net/likelion/bebc25/jpasns/repository/PostRepositoryTest.java
  ```java
  package net.likelion.bebc25.jpasns.repository;

  import net.likelion.bebc25.jpasns.domain.Post;
  import org.junit.jupiter.api.DisplayName;
  import org.junit.jupiter.api.Test;
  import org.springframework.beans.factory.annotation.Autowired;
  import org.springframework.boot.test.context.SpringBootTest;
  import org.springframework.transaction.annotation.Transactional;

  import java.util.List;

  import static org.assertj.core.api.Assertions.assertThat;

  @SpringBootTest
  @Transactional
  class PostRepositoryTest {

      @Autowired
      private PostRepository postRepository;

      @Test
      @DisplayName("본문 키워드 포함 조건 검색")
      void findByContentContaining() {
          // Given: 검색 키워드 지정
          String keyword = "스프링 부트";

          // When: 본문 LIKE %키워드% 조회
          List<Post> posts = postRepository.findByContentContaining(keyword);

          // Then: 반환된 모든 게시글 본문에 키워드 포함 여부 확인
          assertThat(posts).isNotEmpty();
          assertThat(posts).allMatch(post -> post.getContent().contains(keyword));
      }

      @Test
      @DisplayName("특정 좋아요 수 이상인 인기 게시글 목록 필터링 조회")
      void findByLikeCountGreaterThanEqual() {
          // Given: 최소 좋아요 기준 수치
          int minLikeCount = 3;

          // When: 대소 비교(>=) 조건 조회
          List<Post> posts = postRepository.findByLikeCountGreaterThanEqual(minLikeCount);

          // Then: 조건 수치 이상 여부 검증
          assertThat(posts).isNotEmpty();
          assertThat(posts).allMatch(post -> post.getLikeCount() >= minLikeCount);
      }

      @Test
      @DisplayName("특정 회원의 좋아요 수 조건 이상 게시글 최신순 정렬 조회")
      void findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc() {
          // Given: 회원 식별자 및 최소 좋아요 조건
          Long memberId = 2L;
          int minLikeCount = 3;

          // When: 다중 조건 및 정렬 결합 쿼리 메서드 호출
          List<Post> posts = postRepository.findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc(
              memberId, 
              minLikeCount
          );

          // Then: 다중 조건 충족 및 등록일시 내림차순 정렬 상태 검증
          assertThat(posts).isNotEmpty();
          assertThat(posts).allMatch(post -> post.getMember().getId().equals(memberId) && post.getLikeCount() >= minLikeCount);
          assertThat(posts).isSortedAccordingTo((p1, p2) -> p2.getCreatedAt().compareTo(p1.getCreatedAt()));
      }
  }
  ```
- 테스트 검증 핵심 포인트
  - 본문 키워드 검색: `Containing` 키워드를 통해 SQL의 `LIKE %keyword%` 조건이 바인딩되어 대상 키워드를 포함한 게시글만 반환되는지 확인.
  - 대소 비교 필터링: `GreaterThanEqual` 키워드를 통해 지정한 기준 수치 이상의 좋아요를 보유한 레코드만 필터링되는지 확인.
  - 다중 조건 및 정렬 결합: `And` 키워드로 회원 식별자와 좋아요 수 조건을 동시 만족하고, `OrderByCreatedAtDesc`에 의해 최신 등록순으로 정렬되는지 확인.

### 2.1.3 스프링 컨테이너 구동 시점의 정적 검증 메커니즘
- Spring Data JPA는 스프링 애플리케이션이 초기화되는 컨텍스트 로딩 시점에 등록된 모든 리포지토리 인터페이스의 메서드 명명을 전수 검사함.
- 메서드명에 명시된 프로퍼티가 대상 엔티티에 존재하지 않거나 오타가 발생하면 `PropertyReferenceException`을 발생시켜 애플리케이션 구동을 즉시 실패시킴.
- 런타임에 실제 사용자 요청이 인입된 후 쿼리 문법 에러가 발생하는 사고를 방지하고, 초기 구동 단계에서 조기에 휴먼 에러를 탐지하는 안전장치 역할을 수행함.

### 2.1.4 쿼리 메서드의 구조적 한계와 대안 전환 기준
- 조건 절이 3개 이상 늘어나면 메서드명이 지나치게 길어져 코드 가독성과 유지보수성이 급격히 저하됨.
- 연관 엔티티의 복합 조인, 페치 조인 제어, 서브쿼리, 통계 집계 등 복잡한 비즈니스 쿼리를 표현하기 어려움.
- 실무 쿼리 기술 전환 기준
  - 단순 단일 및 2중 조건 조회: 메서드 이름 기반 쿼리 메서드 적용.
  - 다중 조인, 페치 조인, 특정 DTO 직접 매핑, 통계성 정적 쿼리: `@Query`(JPQL) 적용.
  - 다중 검색 필터, 동적 정렬, 가변 조건 기반 동적 쿼리: QueryDSL 적용.

## 2.2 @Query를 활용한 리포지토리 JPQL 선언
메서드 이름 기반 쿼리가 지나치게 길어지거나 복잡한 연관관계 조인, 파라미터 바인딩, DTO 직접 프로젝션이 필요할 때는 `@Query` 어노테이션을 사용하여 리포지토리 메서드에 JPQL을 직접 선언해서 사용.

### 2.2.1 파라미터 바인딩 메커니즘
- 위치 기반 바인딩(`?1`, `?2`): 파라미터 선언 순서가 바뀌면 쿼리 실행 오류나 잘못된 데이터 매핑 사고를 유발하므로 실무 사용을 지양함.
- 이름 기반 바인딩(`:paramName`): `@Param` 어노테이션과 파라미터 이름을 일치시켜 순서와 무관하게 안전하게 매핑되도록 선언하는 실무 표준 방식.

### 2.2.2 JPQL 조인 문법과 묵시적 조인의 위험성
- 명시적 조인(Explicit Join)
  - 내부 조인(INNER JOIN): `SELECT p FROM Post p JOIN p.member m` (연관 데이터가 양쪽에 모두 존재하는 경우만 조회하며 `INNER` 키워드는 생략 가능).
  - 외부 조인(LEFT OUTER JOIN): `SELECT p FROM Post p LEFT JOIN p.member m` (연관된 회원이 없더라도 게시글 기준 데이터를 누락 없이 조회).
- 묵시적 조인(Implicit Join)의 위험성과 원칙
  - 점(`.`) 표기법을 통해 연관 엔티티의 필드에 직접 접근할 때 JPA가 배후에서 SQL 내부 조인을 자동 조립하는 현상 (`SELECT p.member.nickname FROM Post p`).
  - 항상 내부 조인(`INNER JOIN`)으로 번역되므로 연관 데이터가 없는 경우 기준 데이터까지 누락되는 버그를 유발하며, 쿼리 실행 계획을 예측하기 어려움.
  - 실무 원칙: 묵시적 조인은 지양하고, 조인이 필요한 경우에는 항상 `JOIN` 키워드를 명시적으로 선언하여 실행 계획과 쿼리 가독성을 통제함.

### 2.2.3 DTO 프로젝션과 new 문법
- 엔티티를 영속성 컨텍스트에 로딩(1차 캐시 등록)하지 않고, 화면이나 API 응답에 필요한 특정 컬럼만 데이터베이스에서 직접 조회하여 순수 DTO 객체로 즉시 매핑할 때 JPQL의 `new` 문법을 활용함.
- 영속성 관리 배제에 따른 최적화 효과
  - 영속성 컨텍스트(1차 캐시)를 완전히 우회(Bypass)하므로 1차 캐시 엔티티 보관, 스냅샷 생성, 변경 감지(더티 체킹) 연산 오버헤드가 전혀 발생하지 않음.
  - DTO 내부 필드를 수정하더라도 데이터베이스 UPDATE가 발생하지 않는 순수 읽기 전용 데이터로 동작함.
  - 대량 목록 및 통계성 단순 조회 시 힙 메모리 점유율과 가비지 컬렉션(GC) 부하를 대폭 절감함.
- 조회 전용 DTO 분리 원칙과 기존 엔티티 재사용 지양 사유
  - 기존 엔티티에 특정 필드만 받는 생성자를 선언하여 `new Post(...)` 형태로 프로젝션하는 방식은 심각한 부작용을 유발하므로 별도의 조회 전용 DTO(Record)를 설계해야 함.
  - 불완전한 객체로 인한 런타임 오류 방지: 명시한 컬럼만 채워지고 나머지 필드가 null로 비어 있는 불완전한 엔티티가 생성되어, 후속 비즈니스 로직이나 객체 그래프 탐색 시 `NullPointerException`이 발생할 위험이 있음.
  - 데이터 덮어쓰기 오염 방지: 비영속 상태의 불완전한 엔티티 객체를 영속 상태로 오인하여 `save()`나 변경 처리를 시도할 경우, 비어 있던 null 값들이 데이터베이스로 반영되어 기존 데이터가 영구적으로 유실되는 사고를 초래함.
  - 도메인 캡슐화 및 무결성 유지: 화면 요구사항에 맞춘 무분별한 생성자 추가로 도메인 엔티티의 책임이 오염되는 것을 차단하고, 도메인 규칙과 화면 표현 영역을 엄격히 분리함.
- JPQL `SELECT` 절에 DTO 클래스의 전체 패키지 경로를 명시해야 하며, 조회 컬럼 순서 및 타입과 일치하는 생성자가 준비되어 있어야 함.

### 2.2.4 DTO 정의 및 @Query 리포지토리 선언 예시
- 게시글 요약 DTO 정의 (src/main/java/net/likelion/bebc25/jpasns/dto/PostSummaryDto.java)
  ```java
  package net.likelion.bebc25.jpasns.dto;

  public record PostSummaryDto(
      Long postId,
      String memberNickname,
      String content,
      int likeCount
  ) {}
  ```
- PostRepository 인터페이스 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java)
  ```java
      // 특정 회원의 특정 좋아요 수 이상 게시글 최신순 정렬 조회 (조건 누적으로 메서드명이 길어진 순수 쿼리 메서드)
      List<Post> findByMember_IdAndLikeCountGreaterThanEqualOrderByCreatedAtDesc(
          Long memberId, 
          int minLikeCount
      );

      // 메서드 이름이 길어지고 조인이 수반되어 @Query로 직접 선언
      @Query("SELECT p FROM Post p JOIN p.member m WHERE m.id = :memberId AND p.likeCount >= :minLikeCount ORDER BY p.createdAt DESC")
      List<Post> findByMemberAndMinLikes(
          @Param("memberId") Long memberId,
          @Param("minLikeCount") int minLikeCount
      );

      // JPQL new 문법을 활용한 DTO 직접 매핑 조회 (패키지 전체 경로 필수)
      @Query("""
          SELECT new net.likelion.bebc25.jpasns.dto.PostSummaryDto(
              p.id,
              m.nickname,
              p.content,
              p.likeCount
          )
          FROM Post p
          JOIN p.member m
          WHERE m.id = :memberId
      """)
      List<PostSummaryDto> findSummariesByMemberId(@Param("memberId") Long memberId);
  }
  ```

## 2.3 Pageable과 페이징 및 정렬 처리
Spring Data JPA는 페이징을 위해 `Pageable` 인터페이스와 다양한 반환 타입을 제공함.

### 2.3.1 페이징 및 슬라이스 반환 타입
#### 1) `Page<T>`
- 본문 데이터와 함께 전체 데이터 개수를 조회하는 `COUNT(*)` 쿼리를 추가로 실행함.
- 전체 페이지 수, 전체 항목 수, 다음/이전 페이지 존재 여부를 모두 계산해 주므로 일반적인 웹 게시판 페이징 네비게이션에 적합함.

#### 2) `Slice<T>`
- 전체 카운트 쿼리를 실행하지 않고, 요청한 크기(`size`)보다 1개 더 많은 데이터를 조회(`limit size + 1`)하여 다음 데이터의 존재 여부만 확인함.
- 대량 데이터 환경에서 카운트 쿼리 비용을 아낄 수 있어 모바일 앱의 '더보기' 버튼이나 '무한 스크롤' 구현에 최적화됨.

#### 3) `List<T>`
- 카운트 쿼리 없이 지정된 크기만큼의 순수 엔티티 리스트만 반환함.

### 2.3.2 게시글 페이징 조회 서비스 (src/main/java/net/likelion/bebc25/jpasns/service/PostService.java)
  ```java
  public interface PostRepository extends JpaRepository<Post, Long> {
      Page<Post> findByContentContaining(String keyword, Pageable pageable);
  }

  @Transactional(readOnly = true)
  public Page<PostDto.Response> getPostPages(String keyword, int page, int size) {
      Pageable pageable = PageRequest.of(page, size, Sort.by(Sort.Direction.DESC, "id"));
      Page<Post> postPage = postRepository.findByContentContaining(keyword, pageable);

      return postPage.map(PostDto.Response::from);
  }
  ```

### 2.3.3 @Transactional(readOnly = true) 성능 최적화 메커니즘
- 스냅샷 미생성: JPA 구현체는 읽기 전용 트랜잭션 내에서 조회된 엔티티의 초기 상태 스냅샷을 메모리에 보관하지 않으므로 영속성 컨텍스트의 메모리 사용량을 크게 절감함.
- 플러시 생략: 트랜잭션이 종료될 때 변경 감지 연산과 플러시를 수행하지 않으므로 CPU 연산 비용을 건너뜀.
- DB 커넥션 분기: 마스터-슬레이브(Writer-Reader) 복제 환경에서 읽기 전용 트랜잭션 요청을 슬레이브 데이터베이스로 자동 분기 처리함.

# 3. Fetch Join과 연관관계 조회 성능 최적화

## 3.1 N+1 문제의 발생 원인과 시스템 파급력
N+1 문제는 1번의 쿼리로 N건의 엔티티 목록을 가져온 뒤, 각 엔티티에 연관된 지연 로딩 프록시 객체에 접근할 때마다 N번의 추가 조회 쿼리가 반복 실행되어 시스템 리소스를 낭비하는 성능 장애 현상.

### 3.1.1 N+1 발생 과정 및 쿼리 실행 흐름
- 1단계: 피드 게시글 목록을 가져오기 위해 1번의 쿼리 실행 (`SELECT * FROM post LIMIT 10`). 10건의 Post가 반환됨.
- 2단계: 화면에 작성자 닉네임을 출력하기 위해 루프를 돌며 `post.getMember().getNickname()`을 호출함.
- 3단계: 지연 로딩 프록시가 초기화되면서 작성자 10명에 대해 각각 SELECT 쿼리가 10번 실행됨. (총 1 + 10 = 11번의 쿼리 발생)

### 3.1.2 대용량 트래픽 환경에서의 시스템 파급 효과
- 게시글 목록이 10건일 때는 11번의 쿼리로 처리되지만, 데이터가 1,000건인 환경에서는 단 한 번의 화면 조회 요청에 1,001번의 SQL 쿼리가 데이터베이스로 일괄 전송됨.
- 다중 사용자의 동시 요청이 발생할 경우 수만 건의 쿼리가 집중되어 데이터베이스 커넥션 풀 고갈과 시스템 전체 장애를 유발함.

## 3.2 Fetch Join과 컬렉션 페이징 한계 극복

### 3.2.1 JOIN FETCH 동작 원리와 리포지토리 선언
#### 1) JOIN FETCH의 동작 메커니즘
- N+1 문제를 근본적으로 해결하기 위해 JPQL에서 제공하는 성능 최적화 전용 문법인 `JOIN FETCH`를 사용함.
- 단 한 번의 데이터베이스 조인 SQL을 통해 연관된 엔티티 데이터를 즉시 함께 끌어와 1차 캐시에 실제 엔티티로 채워 넣으므로 추가 쿼리가 전혀 발생하지 않음.

#### 2) Fetch Join 리포지토리 메서드 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java)
  ```java
  public interface PostRepository extends JpaRepository<Post, Long> {

      // 단 한 번의 조인 쿼리로 Post와 Member를 즉시 로딩하여 N+1 방지
      @Query("""
          SELECT p FROM Post p
          JOIN FETCH p.member
          ORDER BY p.id DESC
      """)
      List<Post> findAllWithMember();
  }
  ```

### 3.2.2 컬렉션 페치 조인 시 페이징 불가의 원인
- `@ManyToOne`이나 `@OneToOne` 같은 단일 객체 연관관계는 조인을 하더라도 데이터 행 수가 늘어나지 않으므로 `JOIN FETCH`와 페이징(`Pageable`)을 함께 사용해도 정상 동작함.
- 그러나 일대다(`@OneToMany`) 컬렉션(예: `Post`와 `Comment` 목록)을 페치 조인하면 데이터베이스 1:N 조인 결과 데이터가 자식 레코드 수만큼 중복 행으로 증폭됨.
- 이 상태에서 페이징을 시도하면 데이터베이스 수준에서 `LIMIT`/`OFFSET`을 적용하지 못하고 전체 테이블 데이터를 메모리로 무작정 퍼 올린 뒤 메모리에서 잘라내는 위험한 경고(`HHH000104: firstResult/maxResults specified with collection fetch; applying in memory!`)가 발생하여 메모리 고갈(OOM)을 유발함.

### 3.2.3 Batch Size를 활용한 컬렉션 페이징 한계 극복
#### 1) 컬렉션 페이징과 N+1 문제의 표준 해결 공식
- ToOne(다대일, 일대일) 연관관계는 페치 조인으로 묶어 쿼리 횟수를 줄이고 페이징을 정상 적용함.
- ToMany(일대다) 컬렉션은 페치 조인을 걸지 않고 지연 로딩(LAZY)을 그대로 유지함.
- 지연 로딩으로 인해 발생하는 N+1 문제를 방지하기 위해 `application.yaml`에 글로벌 배치 페치 사이즈(`default_batch_fetch_size`) 옵션을 선언함.

#### 2) 글로벌 배치 페치 사이즈 설정 (application.yaml)
  ```yaml
  spring:
    jpa:
      properties:
        hibernate:
          default_batch_fetch_size: 100
  ```

#### 3) Batch Size 동작 메커니즘
- 연관된 지연 로딩 컬렉션을 조회할 때 엔티티 1건마다 단건 쿼리를 반복 실행하지 않고, 지정한 크기(100)만큼 `WHERE post_id IN (?, ?, ...)` 절로 묶어서 한 번에 일괄 조회함.
- 10개의 게시글에 달린 댓글을 가져올 때 기존 1 + 10번 실행되던 쿼리가 1 + 1번으로 압축되므로, 컬렉션 페이징 한계를 우회하면서 N+1 문제까지 해결함.
- 시스템 메모리와 DB 쿼리 파라미터 제약을 고려하여 보통 100~1000 사이의 수치를 권장함.

## 3.3 @EntityGraph를 활용한 선언적 페치 조인

### 3.3.1 @EntityGraph의 정의 및 주요 속성
- JPQL에 `JOIN FETCH` 구문을 일일이 작성하지 않고도 선언적으로 페치 조인을 적용할 수 있는 Spring Data JPA 어노테이션.
- 주요 속성과 기본값:
  - `attributePaths`: 함께 즉시 로딩할 연관 엔티티 필드명을 배열로 지정함 (기본값: 빈 배열 `{}`).
  - `type`: 엔티티 그래프 적용 방식을 지정함 (기본값: `EntityGraphType.FETCH`, 명시한 속성은 EAGER 로딩하고 나머지는 LAZY 로딩함).
- 기본적으로 LEFT OUTER JOIN으로 실행되어 연관 엔티티가 없더라도 부모 데이터를 누락 없이 가져옴.

### 3.3.2 @EntityGraph 적용 리포지토리 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java)
  ```java
  public interface PostRepository extends JpaRepository<Post, Long> {

      @EntityGraph(attributePaths = {"member"})
      List<Post> findAll();
  }
  ```

# 4. 벌크 연산과 영속성 컨텍스트 동기화

## 4.1 대량 데이터 수정/삭제와 @Modifying
- 단건 변경 감지는 엔티티 개수만큼 UPDATE SQL이 각각 실행되므로, 수천 건 이상의 데이터를 한 번에 수정할 때는 쿼리 한 번으로 처리하는 벌크 연산(Bulk Operation)이 필요함.
- Spring Data JPA에서 INSERT, UPDATE, DELETE 구문을 직접 정의할 때는 반드시 `@Modifying` 어노테이션을 함께 붙여야 하며, 누락 시 `InvalidDataAccessApiUsageException`이 발생함.

## 4.2 벌크 연산 후 1차 캐시 데이터 불일치 해결

### 4.2.1 1차 캐시 데이터 불일치 원인
- 벌크 연산은 영속성 컨텍스트(1차 캐시)를 완전히 무시하고 데이터베이스에 직접 쿼리를 날려 데이터를 변경함.
- 이로 인해 1차 캐시에 이미 올라와 있는 엔티티의 데이터와 DB 실제 데이터가 달라지는 데이터 불일치 문제가 발생함.

### 4.2.2 @Modifying 옵션을 통한 영속성 컨텍스트 동기화
- `flushAutomatically`: 벌크 연산 실행 직전에 영속성 컨텍스트의 변경 사항을 DB에 먼저 동기화할지 여부를 지정함 (기본값: false).
- `clearAutomatically`: 벌크 연산 실행 직후 영속성 컨텍스트 1차 캐시를 비워, 이후 조회 시 DB의 최신 데이터를 다시 읽어오도록 강제할지 여부를 지정함 (기본값: false).

### 4.2.3 좋아요 수 일괄 증가 벌크 연산 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepository.java)
  ```java
  public interface PostRepository extends JpaRepository<Post, Long> {

      @Modifying(clearAutomatically = true, flushAutomatically = true)
      @Query("UPDATE Post p SET p.likeCount = p.likeCount + 1 WHERE p.id = :postId")
      int incrementLikeCount(@Param("postId") Long postId);
  }
  ```

# 5. QueryDSL 동적 쿼리와 커스텀 리포지토리

## 5.1 QueryDSL 도입 배경과 QClass 생성 메커니즘

### 5.1.1 런타임 오류와 컴파일 타임 검증의 차이
- JPQL은 문자열 형태로 쿼리를 작성하므로 컬럼명이나 엔티티명에 오탈자가 있어도 개발 단계에서 사전에 인지하기 어려우며, 애플리케이션 구동 후 해당 쿼리가 실제로 호출되는 시점에 런타임 SQL 예외가 발생함.
- QueryDSL은 문자열 대신 자바 코드로 쿼리를 작성하는 빌더 라이브러리에 해당함.
- 자바 컴파일러가 엔티티 메타 모델 기반으로 타입 체크를 수행하므로, 문법 오류나 필드명 오탈자를 컴파일 시점에 즉시 검출하여 안정성을 확보할 수 있음.

### 5.1.2 빌드 의존성 및 APT 설정

## 5.2 기본 문법과 Where 다중 파라미터 동적 쿼리

### 5.2.1 QClass 필드 접근과 쿼리 체이닝
#### 1) QClass 정적 임포트와 쿼리 체이닝
- QClass를 정적 임포트(`import static ... QPost.post;`)하여 체이닝 방식으로 쿼리를 작성함.

#### 2) QueryDSL 기본 조회 리포지토리 (src/main/java/net/likelion/bebc25/jpasns/repository/PostQueryRepository.java)
  ```java
  package net.likelion.bebc25.jpasns.repository;

  import com.querydsl.jpa.impl.JPAQueryFactory;
  import net.likelion.bebc25.jpasns.domain.Post;
  import org.springframework.stereotype.Repository;
  import java.util.List;

  import static net.likelion.bebc25.jpasns.domain.QPost.post;
  import static net.likelion.bebc25.jpasns.domain.QMember.member;

  @Repository
  public class PostQueryRepository {

      private final JPAQueryFactory queryFactory;

      public PostQueryRepository(JPAQueryFactory queryFactory) {
          this.queryFactory = queryFactory;
      }

      public List<Post> findPostsByMemberNickname(String memberNickname) {
          return queryFactory
                  .selectFrom(post)
                  .join(post.member, member).fetchJoin()
                  .where(member.nickname.eq(memberNickname))
                  .orderBy(post.id.desc())
                  .fetch();
      }
  }
  ```

### 5.2.2 Where 다중 파라미터 기반 동적 쿼리
#### 1) BooleanBuilder 방식과 Where 다중 파라미터 비교
- 검색 조건(키워드, 최소 좋아요 수, 작성자명 등)이 입력될 수도 있고 비어있을 수도 있는 동적 쿼리를 처리할 때, `BooleanBuilder` 객체를 생성하는 방식보다 `BooleanExpression`을 반환하는 개별 메서드를 선언하여 `where(...)` 절에 나열하는 방식을 권장함.
- QueryDSL의 `where()` 메서드는 인자로 전달된 조건 중 `null` 값은 자동으로 무시하므로 코드가 극도로 간결해짐.
- 메서드들을 조합하여 재사용할 수 있는 큰 장점이 있음.

#### 2) SNS 게시글 복합 동적 검색 구현 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepositoryImpl.java)
  ```java
  public List<Post> searchPosts(PostSearchCondition condition) {
      return queryFactory
              .selectFrom(post)
              .join(post.member, member).fetchJoin()
              .where(
                      contentContains(condition.contentKeyword()),
                      likeCountGoe(condition.minLikeCount()),
                      memberNicknameEq(condition.memberNickname())
              )
              .fetch();
  }

  private BooleanExpression contentContains(String contentKeyword) {
      return StringUtils.hasText(contentKeyword) ? post.content.contains(contentKeyword) : null;
  }

  private BooleanExpression likeCountGoe(Integer minLikeCount) {
      return minLikeCount != null ? post.likeCount.goe(minLikeCount) : null;
  }

  private BooleanExpression memberNicknameEq(String memberNickname) {
      return StringUtils.hasText(memberNickname) ? member.nickname.eq(memberNickname) : null;
  }
  ```

## 5.3 Spring Data JPA 커스텀 리포지토리 연동

### 5.3.1 사용자 정의 리포지토리 3단계 패턴
Spring Data JPA 리포지토리에서 QueryDSL 동적 쿼리 메서드를 한 번에 호출할 수 있도록 결합하는 표준 구조.

#### 1) 사용자 정의 리포지토리 3단계 아키텍처
- 1단계: 사용자 정의 인터페이스 생성 (`PostRepositoryCustom`).
- 2단계: 사용자 정의 구현 클래스 작성 (`PostRepositoryImpl` - 반드시 접미사에 `Impl`을 붙여야 스프링이 인식함).
- 3단계: 기본 리포지토리에서 다중 상속 통합 (`PostRepository extends JpaRepository<Post, Long>, PostRepositoryCustom`).

#### 2) 커스텀 인터페이스 및 구현 클래스 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepositoryCustom.java)
  ```java
  // 1. 커스텀 인터페이스 정의
  public interface PostRepositoryCustom {
      List<Post> search(PostSearchCondition condition);
      Page<Post> searchPage(PostSearchCondition condition, Pageable pageable);
  }
  ```
  ```java
  // 2. QueryDSL 구현체 작성 (Impl 접미사 필수)
  @RequiredArgsConstructor
  public class PostRepositoryImpl implements PostRepositoryCustom {

      private final JPAQueryFactory queryFactory;

      @Override
      public List<Post> search(PostSearchCondition condition) {
          return queryFactory
                  .selectFrom(post)
                  .join(post.member, member).fetchJoin()
                  .where(
                          contentContains(condition.contentKeyword()),
                          likeCountGoe(condition.minLikeCount())
                  )
                  .fetch();
      }

      private BooleanExpression contentContains(String keyword) {
          return StringUtils.hasText(keyword) ? post.content.contains(keyword) : null;
      }

      private BooleanExpression likeCountGoe(Integer likeCount) {
          return likeCount != null ? post.likeCount.goe(likeCount) : null;
      }
  }
  ```

### 5.3.2 PageImpl을 활용한 표준 페이징 처리
#### 1) PageImpl 페이징 처리 메커니즘
- QueryDSL로 조회한 본문 데이터 목록과 전체 카운트 수를 조합하여 Spring Data JPA의 `Page<T>` 구현체인 `PageImpl`로 반환하는 표준 방식.
- 본문 쿼리에 `offset()`과 `limit()`을 적용하여 필요한 구간만 가져오고, 카운트 쿼리를 별도로 실행하여 총 데이터 건수를 구한 뒤 `new PageImpl<>(content, pageable, total)`로 감싸서 반환함.

#### 2) 표준 페이징 구현 (src/main/java/net/likelion/bebc25/jpasns/repository/PostRepositoryImpl.java)
  ```java
  @Override
  public Page<Post> searchPage(PostSearchCondition condition, Pageable pageable) {
      // 1. 페이징 본문 데이터 조회 (offset, limit 적용)
      List<Post> content = queryFactory
              .selectFrom(post)
              .join(post.member, member).fetchJoin()
              .where(
                      contentContains(condition.contentKeyword()),
                      likeCountGoe(condition.minLikeCount())
              )
              .offset(pageable.getOffset())
              .limit(pageable.getPageSize())
              .fetch();

      // 2. 전체 건수 집계 카운트 쿼리
      Long total = queryFactory
              .select(post.count())
              .from(post)
              .where(
                      contentContains(condition.contentKeyword()),
                      likeCountGoe(condition.minLikeCount())
              )
              .fetchOne();

      long totalCount = total != null ? total : 0L;

      // 3. PageImpl로 포장하여 반환
      return new PageImpl<>(content, pageable, totalCount);
  }
  ```

# 6. 단위 및 통합 테스트 케이스 작성

## 6.1 기본 쿼리 메서드 및 페이징/벌크 연산 테스트
- 테스트 목표
  - JpaRepository가 기본 제공하는 CRUD 메서드(`save`, `findById`, `deleteById`)의 정상 동작을 확인함.

  ```java
      @Test
  ```

# 7. JPA 핵심 트러블슈팅 FAQ

## 7.1 엔티티 기본 생성자 누락 오류
- 현상: `org.hibernate.InstantiationException: No default constructor for entity` 예외 발생.
- 원인: JPA 구현체인 하이버네이트는 런타임에 리플렉션 기술을 통해 동적으로 엔티티 객체를 생성함. 이때 매개변수가 없는 기본 생성자가 반드시 존재해야 객체를 생성할 수 있음.
- 해결: 롬복의 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`를 엔티티 클래스 상단에 선언함. 외부에서 무분별하게 빈 객체를 `new`로 생성하는 것을 방지하면서 JPA 스펙 요구사항을 만족시키는 표준 방식.

## 7.2 트랜잭션 종료 후 지연 로딩 예외
- 현상: `org.hibernate.LazyInitializationException: could not initialize proxy - no Session` 예외 발생.
- 원인: 서비스 계층에서 트랜잭션이 끝나 영속성 컨텍스트가 닫힌 이후, 컨트롤러나 화면 뷰에서 아직 초기화되지 않은 지연 로딩 연관 엔티티의 getter를 호출했을 때 발생함.
- 해결: 컨트롤러로 엔티티를 그대로 넘기지 말고, 서비스 계층 트랜잭션 내부에서 필요한 데이터를 조회하여 DTO로 변환하여 반환하거나, 리포지토리에서 Fetch Join을 적용하여 연관 객체를 한 번에 미리 조회해 두어야 함.

## 7.3 양방향 순환 참조와 StackOverflowError
- 현상: REST 컨트롤러에서 엔티티를 직접 반환할 때 JSON 응답이 끝나지 않고 반복되다가 `java.lang.StackOverflowError` 발생.
- 원인: Post 객체를 JSON으로 바꿀 때 Comment 목록을 읽고, 다시 Comment 안의 Post를 읽으면서 Jackson 직렬화가 두 참조를 무한 호출함.
- 해결: 웹 계층과 데이터베이스 계층의 결합을 끊기 위해 컨트롤러 응답 반환 타입으로 엔티티를 절대 직접 사용하지 않고, 반드시 순수 데이터만 담긴 응답 DTO를 정의하여 변환 반환함.

## 7.4 쿼리 메서드 명명 규칙 위반 오류
- 현상: 애플리케이션 시작 시점에 `org.springframework.data.mapping.PropertyReferenceException: No property 'xxx' found for type 'Entity'` 예외 발생하며 서버 기동 실패.
- 원인: 리포지토리 인터페이스에 작성한 쿼리 메서드 이름에 오탈자가 있거나, 엔티티 클래스에 존재하지 않는 필드명을 메서드 이름에 조합했을 때 발생함.
- 해결: 에러 로그에 출력된 프로퍼티 이름을 확인하고, 엔티티의 실제 자바 필드명(대소문자 포함)과 리포지토리 메서드 이름을 정확히 일치시킴. 복잡한 다중 조건은 메서드 이름을 길게 쓰지 말고 `@Query`나 QueryDSL로 전환함.

## 7.5 벌크 연산 후 1차 캐시 데이터 불일치
- 현상: `@Query`로 UPDATE 벌크 연산을 성공적으로 실행했으나, 동일 트랜잭션 내에서 `findById()`로 다시 조회하면 수정 전 이전 데이터가 그대로 조회됨.
- 원인: 벌크 연산은 영속성 컨텍스트 1차 캐시를 거치지 않고 DB에 직접 쿼리를 날리므로, 1차 캐시에는 여전히 과거 스냅샷 데이터가 남아있기 때문.
- 해결: 리포지토리 벌크 메서드 상단에 `@Modifying(clearAutomatically = true)` 옵션을 선언하여 벌크 쿼리 실행 직후 1차 캐시를 비우도록 강제함.
